## Note (mise à jour après le bilan Phase 5)

Ce fichier est la source de vérité pour prioriser les prochains modules après le POC.

La priorité initialement suggérée ("Back-office/CMS léger d'abord") est en grande partie déjà couverte par l'admin construit en Phase 3 (`/admin` : toggle modules + édition contenu/offres, protégé par mot de passe). Reste à durcir avant un vrai client (voir `05-roadmap-poc.md`, bilan Phase 5) plutôt qu'à construire de zéro : mot de passe unique en clair → à remplacer par un vrai compte/hash, `module.meta.json`/`*.config.ts` non exploités par l'admin (noms de modules bruts au lieu de noms lisibles), pas de gestion multi-utilisateurs.

Priorité suggérée pour le premier vrai module métier après le POC : **RDV** ou **Newsletter** (forte demande probable chez tes prospects locaux, et bons candidats pour re-valider le pattern module sur un cas avec plus de logique métier que Blog — récurrence, créneaux, envoi d'email).

## Catalogue produits (ajouté le 2026-07-26)

Demandé par Ethan : catalogue de produits (photos, prix, description) avec gestion de stock, étendu à un panier + une commande (décision confirmée par Ethan plutôt qu'un simple catalogue vitrine). N'existait pas dans la grille tarifaire d'origine — **à Ethan de décider où le positionner tarifairement**, ce fichier ne fait qu'enregistrer ce qui a été construit.

**Ce qui est fait** : produits multi-photos (upload admin, stockage local `backend/wwwroot/uploads/`, servi via fichiers statiques), stock, panier côté client (React Context + `localStorage`), commande qui décrémente le stock en base dans une transaction, page admin "Commandes" pour marquer une commande traitée ou l'annuler (l'annulation restaure le stock).

**Mise à jour du 2026-07-29** : le paiement en ligne réel est arrivé avec le module Stripe (voir plus bas), qui se branche sur ce flux de commande plutôt que de le dupliquer, comme anticipé ci-dessous. Le paiement sur place (commande enregistrée sans encaissement) a été retiré à la demande d'Ethan — Stripe est désormais la seule façon de finaliser une commande.

**Mise à jour du 2026-08-06 — avis produits** : suite du même brainstorm. Jusqu'ici un produit n'affichait que nom/prix/description/stock, aucun retour client visible — pas de fiche produit publique non plus (le catalogue n'affichait que des cards avec "Ajouter au panier" direct). Question posée à Ethan avant de coder (pas de fiche produit existante pour lire le texte des avis) : note moyenne sur la card + modale au clic (avis complets + formulaire), ou juste la note sans le texte ? Réponse : la modale.

- Nouvelle entité `ProductReview` (`modules/catalogue/backend/ProductReview.cs`), même pattern de curation que `GoogleReview.Selected` (module Avis Google) — soumis librement par n'importe quel visiteur (pas de vérification d'achat en V1), jamais visible tant que le client ne l'a pas approuvé depuis la fiche produit de son admin (`ProductDetailPage.tsx`, nouvelle section "Avis").
- `GET /catalogue/products` renvoie désormais `averageRating`/`reviewCount` par produit (calculés en une seule requête agrégée, pas de N+1), affichés en étoiles sur chaque card.
- Cliquer une card ouvre une modale (même esprit que la lightbox de Galerie) : description complète, avis approuvés, formulaire pour en laisser un.

**Mise à jour du 2026-08-06 — email de confirmation de commande** : suite du brainstorm de fonctionnalités manquantes (`docs/07-admin-global.md`). Jusqu'ici l'acheteur n'avait *aucune* trace de sa commande au-delà d'une bannière transitoire sur la page catalogue (prix ou message générique, disparaît si l'onglet est fermé) — pas d'email, pas de page consultable plus tard (voir `CatalogueSection.tsx`, `CheckoutReturnBanner`). `StripeModule.cs` envoie maintenant un email de confirmation (récapitulatif + total) via le webhook, best-effort comme le reste des emails automatiques du projet. Réutilise le compte Brevo déjà partagé par l'agence (aucun tenant n'a le sien, même décision que côté facturation agence) : l'adresse d'expédition technique reste celle de l'agence (seule adresse vérifiée dans Brevo), mais le nom affiché est celui du site du tenant et les réponses partent directement chez lui (`replyTo` = `SiteContent.Email`). **Limite V1 assumée** : toujours pas de page de suivi de commande publique — l'email est la seule trace persistante pour l'acheteur.

**Mise à jour du 2026-07-31** : le stock exact n'est plus affiché publiquement (juste "Ajouter au panier", ou "Rupture de stock" sans nombre) ; le panier passe d'un tiroir à une vraie page dédiée (`/t/{clientSiteId}/panier`, identique pour tous les templates) où le client ajuste ses quantités et renseigne nom/email/téléphone/adresse avant de payer. Voir `docs/05-roadmap-poc.md` pour le détail technique.

**Mise à jour du 2026-08-06 — refonte du panier** : retour d'Ethan après capture d'écran de la page `/panier` en l'état (formulaire sans labels, adresse en simple texte libre, aucune case légale, page toujours en colonne unique même en grand écran). Trois correctifs :

- **Autocomplete d'adresse** : le champ "Adresse de livraison" utilise désormais Google Places, comme les autres champs adresse de l'admin (`EstablishmentSection.tsx`, `AddressAutocomplete` dans `frontend/src/pages/agency/shared.tsx`). Problème : ces routes existantes exigent une session admin (`TenantAdminAuth`/`AdminAuth`), inutilisable depuis une page publique. Ajout d'une route dédiée **sans authentification** (`GET /api/t/{clientSiteId}/google-places/search`, `backend/GooglePlacesEndpoints.cs`) — gardée par le module Catalogue (404 si non activé) et par une nouvelle policy de rate-limiting (`public-places`, 15 req/min/IP, `backend/Program.cs`) pour limiter l'abus vu que chaque appel consomme du quota Google payant.
- **Mise en page desktop** : grille deux colonnes à partir de `lg:` — colonne principale (panier interactif + formulaire + case légale + bouton de paiement) et colonne récapitulative sticky (photo + description + quantité par article, repris de `CatalogueSection.tsx`/`CartContext.tsx` qui stockent maintenant `imagePath`/`description` par ligne du panier). Reste en une seule colonne empilée sur mobile.
- **Case légale obligatoire** : case à cocher "J'ai lu et j'accepte les conditions générales de vente", requise pour activer le bouton de paiement (comme `namePlaceholder`/`emailPlaceholder` déjà requis).

**Mise à jour du 2026-08-06 — CGV obligatoires, pas une page libre optionnelle** : première implémentation de la case légale ci-dessus, la case cherchait un lien parmi les pages libres du module Pages (payant, optionnel) — remarque d'Ethan : les CGV ne sont pas une fonctionnalité premium, c'est une obligation légale, le site ne devrait pas pouvoir vendre sans. Question posée avant de coder (texte générique auto-rempli / paiement bloqué tant que non rédigées / simple rappel admin non bloquant) : Ethan a choisi de bloquer le paiement.

- Nouveau champ dédié `SiteContent.CgvContent` (HTML riche, même éditeur TipTap que Blog/Pages) plutôt qu'une page du module Pages — reste disponible même sur un site sans ce module. Édité depuis un nouvel onglet "CGV" dans `EstablishmentSection.tsx` (à côté d'Informations/Photos/Horaires), affiché publiquement sur une page dédiée `/t/{clientSiteId}/cgv` (`frontend/src/pages/CgvPage.tsx`, hors module puisque le contenu est "core").
- Tant que Catalogue + Stripe sont actifs et que ce champ est vide : le bouton "Payer par carte" du panier public est remplacé par un message ("paiementUnavailable"), et un bandeau d'avertissement apparaît dans l'admin sur `EstablishmentSection.tsx` (onglet CGV) et `DashboardSection.tsx` (Tableau de bord) pour qu'Ethan/le client ne l'oublie pas avant de mettre le site en ligne.
